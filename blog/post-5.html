Python 自动化测试入门实战：从第一个用例到 Allure 报告

配套《Python 自动化测试学习导图》的实战篇。断言、参数化、fixture、mock、接口测试、Playwright + POM、覆盖率与报告，一条命令一条命令地走完。

上一篇我画了一张学习导图，把 Python 自动化测试要学的东西铺成了一张地图。地图看完，下一步就是落地。这篇不讲概念，只讲「怎么把第一个能跑的测试体系搭起来」——每一步都配了可以直接复制的代码。

技术选型很直接：pytest 做框架，requests + responses 做接口，Playwright 做 UI，pytest-cov 看覆盖率，Allure 出报告。这套组合在 2026 年是新项目最省心的默认解。

配套示例工程已经跑通，目录在 python-testing-demo/：clone 下来装完依赖就能 pytest。文章里所有代码都来自它。

一、先把工程骨架立起来

测试代码最容易死在「随手一放」：脚本散在各个目录，谁都能改，谁都不敢删。建议一开始就按约定分目录：

python-testing-demo/
├── pytest.ini                 测试配置：markers、pythonpath
├── requirements.txt
├── src/                       被测代码
├── pages/                     页面对象模型（POM）
└── tests/
    ├── conftest.py            共享夹具
    ├── test_calculator.py     参数化
    ├── test_user_service.py   mock
    ├── test_api_orders.py     接口
    ├── fixtures/demo.html     UI 用例用的本地页面
    └── ui/test_search.py      Playwright 用例

pytest.ini 是整个体系的开关，先写好它：

[pytest]
testpaths = tests
pythonpath = .
addopts = -ra
markers =
    smoke: 冒烟用例，最快的一批
    api: 接口测试
    ui: UI 端到端测试，需要浏览器
    slow: 耗时用例
  • testpaths：不敲路径也知道去哪儿找用例
  • pythonpath = .：让 import src.xxx 直接可用（pytest ≥ 7）
  • markers：先注册再使用，否则会刷一堆警告

依赖就这些：

pip install pytest requests responses pytest-mock pytest-cov \
            pytest-playwright allure-pytest faker
playwright install chromium        # 只有跑 UI 用例才需要

二、第一个测试：断言与异常

pytest 的哲学是「用 Python 原生的 assert，别的都别管」。它会在失败时自动展开表达式的中间值，比任何断言库的报错都清楚。

def test_divide_ok():
    assert divide(10, 4) == 2.5


def test_divide_by_zero_raises():
    """异常断言要用 pytest.raises，别用 try/except 自己判断。"""
    with pytest.raises(ValueError) as exc:
        divide(1, 0)
    assert "除数不能为 0" in str(exc.value)

两个约定要记牢：文件名必须 test_*.py，函数必须 test_* 开头；比较浮点数用 pytest.approx，别直接 ==。

三、参数化：一份逻辑，多组数据

写十遍差不多的用例是自动化测试最大的浪费。parametrize 把「数据」和「逻辑」分开，加一组边界值只需要加一行：

@pytest.mark.smoke
@pytest.mark.parametrize(
    "a, b, expected",
    [
        (1, 2, 3),
        (0, 0, 0),
        (-1, 1, 0),
        (10 ** 6, 10 ** 6, 2 * 10 ** 6),
    ],
    ids=["small", "zero", "negative", "big"],   # 让报告里的名字可读
)
def test_add(a, b, expected):
    assert add(a, b) == expected

ids 是个容易被忽略的好习惯：默认参数化用例名是 test_add[1-2-3]，加了 ids 之后变成 test_add[zero]，失败时一眼就知道是哪组数据。

四、fixture 与 conftest：测试的地基

fixture 是 pytest 最值得花时间学的东西。它同时承担三件事：前置准备、后置清理、依赖注入。

@pytest.fixture(scope="session")
def base_url(env):
    return {
        "test": "https://api.test.example.com",
        "staging": "https://api.staging.example.com",
        "prod": "https://api.example.com",
    }[env]


@pytest.fixture
def api_client(base_url):
    """yield 之前是前置，yield 之后是后置（一定会执行，哪怕用例失败）。"""
    import requests

    session = requests.Session()
    session.headers.update({"Authorization": "Bearer test-token"})

    yield session          # ← 用例在这里执行

    session.close()        # ← 收尾：关连接、清数据

两条经验：

  • 作用域按成本定：function（默认，用例间完全隔离）< class < module < session。建连接、读配置用 session；造用户数据用 function，别为了快而共享可变状态。
  • 共享的放 conftest.py：放在 tests/ 下的 conftest 会被该目录及子目录自动加载，用例里不用 import，直接把夹具名写成参数就行。

conftest 里还能注册自定义命令行参数，一套代码切环境：

def pytest_addoption(parser):
    parser.addoption("--env", action="store", default="test",
                     help="运行环境：test / staging / prod")

@pytest.fixture(scope="session")
def env(request):
    return request.config.getoption("--env")

然后就可以 pytest --env=staging 了。

五、mock：只测自己的逻辑

外部依赖（第三方接口、数据库、时间、随机数）一律 mock 掉。装了 pytest-mock 之后，用 mocker 夹具即可，不用操心 patch 的启停：

def test_display_name_with_mock(mocker):
    client = mocker.Mock()
    client.fetch.return_value = {"id": 1, "name": " chopper ", "active": True}

    service = UserService(client)

    assert service.display_name(1) == "Chopper"
    client.fetch.assert_called_once_with(1)     # 顺带校验调用方式


def test_monkeypatch_env(monkeypatch):
    """monkeypatch 是内置夹具，适合改环境变量、改配置值。"""
    monkeypatch.setenv("API_TOKEN", "abc123")
打补丁要打在「被查找的地方」，不是「定义的地方」。from a import f 之后再 mocker.patch("a.f") 是无效的，得 patch 使用方模块里的名字。

六、接口测试：拦掉真实 HTTP

接口用例最怕不稳定。responses 直接在请求层拦截，不启服务、不依赖后端，跑起来又快又稳：

@responses.activate
def test_get_order_by_id(base_url):
    responses.add(
        responses.GET,
        f"{base_url}/orders/1001",
        json={"id": 1001, "status": "paid", "amount": 59.9},
        status=200,
    )

    resp = requests.get(f"{base_url}/orders/1001", timeout=5)

    assert resp.status_code == 200
    body = resp.json()
    assert body["status"] == "paid"
    assert body["amount"] < 100

参数化 + mock 组合起来，可以把所有状态分支一次枚举完：@pytest.mark.parametrize("status", ["paid", "unpaid", "refunded"])。

测试数据别手写死，用 faker 每次生成不一样的：

from faker import Faker
fake = Faker("zh_CN")

payload = {"name": fake.name(), "phone": fake.phone_number()}

看似琐碎，但硬编码数据最容易漏掉边界：超长姓名、带区号的电话、含 emoji 的地址。

七、UI 测试：Playwright + POM

2026 年新项目选 Playwright 基本没有争议：自带等待、并发、追踪，Python 版 API 也足够干净。装 pytest-playwright 后直接能用 page 夹具。

关键是别把选择器写进用例里。页面对象模型（POM）把页面结构收在一处：

class SearchPage:
    def __init__(self, page: Page):
        self.page = page
        self.input = page.locator("#q")
        self.button = page.locator("#go")
        self.results = page.locator("#results li")

    def open(self, url):
        self.page.goto(url)
        return self                    # 返回 self 好做链式调用

    def search(self, keyword):
        self.input.fill(keyword)
        self.button.click()
        return self

    def result_texts(self):
        return self.results.all_inner_texts()

用例就只剩「做什么」和「期望什么」：

@pytest.mark.ui
def test_search_filters(search_page):
    search_page.search("果")
    expect(search_page.results).to_have_count(1)
    assert "苹果" in search_page.result_texts()

三条避坑经验：

  • 永远别 time.sleep。用 expect(...).to_have_*，它会自动重试到超时，这是 Playwright 相对 Selenium 最大的效率来源。
  • UI 用例不要依赖外网。示例工程里用 file:// 打开本地 demo.html，离线也能跑，CI 里也不会因为第三方站点抖动而红。
  • UI 只做主干，别做穷举。等价类、边界值这些应该压在接口和单元测试层——测试金字塔不是口号，是维护成本的账。

八、覆盖率：知道哪里没测

pytest --cov=src --cov-report=term-missing --cov-report=html

term-missing 会直接列出没覆盖到的行号，比一个孤零零的百分比有用得多。追求 100% 覆盖率没有意义，但「新增代码有没有被测到」必须有答案——把覆盖率阈值放进 CI 就够用了。

九、Allure 报告：让结果能拿去汇报

pytest --alluredir=allure-results
allure serve allure-results      # 需要本机装 Allure CLI（依赖 Java 8+）

装 allure-pytest 后，用装饰器给用例加上业务语义，报告才不是一堆函数名：

import allure

@allure.epic("订单中心")
@allure.feature("订单查询")
@allure.story("按 ID 查询已支付订单")
def test_get_order_by_id(base_url):
    with allure.step("请求订单详情"):
        ...
    allure.attach("请求参数", '{"id": 1001}', allure.attachment_type.JSON)

失败截图也可以一并塞进报告，UI 用例尤其建议加：

@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    if report.when == "call" and report.failed:
        page = item.funcargs.get("page")
        if page:
            allure.attach(page.screenshot(), "失败截图",
                          allure.attachment_type.PNG)

这段放 conftest.py 里，全局生效。

十、接进 CI：跑不起来的测试等于没有

name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: playwright install --with-deps chromium
      - run: pytest --cov=src --cov-report=xml --alluredir=allure-results
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: allure-results
          path: allure-results

最后一步的 if: always() 很重要：测试失败时也要把结果传上来，否则红灯了你却看不到报告。

十一、命令速查

命令作用
pytest跑全部用例
pytest -m smoke只跑冒烟
pytest -m "not ui"跳过 UI（无需浏览器）
pytest -k zero按名字关键字挑用例
pytest -x -q首次失败即停，安静输出
pytest --lf只跑上次失败的
pytest --env=staging自定义参数切环境
pytest --cov=src --cov-report=html生成覆盖率网页

十三、几个新手一定会踩的坑

  • 用例之间有依赖：A 用例造的数据被 B 用，结果单独跑 B 就红。每个用例必须能独立运行，数据一律用 fixture 造、用 fixture 清。
  • fixture 作用域开太大：为了「快」把可变状态提到 session 级，很快就会出现莫名其妙的偶发失败。
  • mock 打错位置：patch 的是使用方模块里的名字，不是定义处。
  • 断言太弱：assert resp 等于没写。要断言状态码、关键字段、字段类型。
  • UI 用例当功能测试用：一条 UI 用例几秒到几十秒，几百条之后 CI 就没人愿意等了。

小结

整套体系拆开看其实只有五件事：用例怎么写（断言 + 参数化）、准备工作怎么复用（fixture + conftest）、外部依赖怎么隔离（mock + responses）、UI 怎么组织（Playwright + POM）、结果怎么交付（覆盖率 + Allure + CI）。

先把这套最小闭环跑通，再往里加数据库测试、异步测试、并发跑批、AI 辅助定位——那时候你补的就是能力，而不是在补地基。回头看那张导图，主干这几条也就都点亮了。
